# Digitalis CSS System — Spec v0.7

**Status:** Draft
**Scope:** Practice-level CSS architecture for Digitalis Web Corp projects

---

## 0. System Layers

This system has three layers. Each has a distinct role, stability profile and scope.

| Layer | What it contains | Stability | Scope |
|---|---|---|---|
| **Spec** (this document) | Architecture, conventions, rules | Stable, rarely changes | Every project follows this |
| **Library** (`lib/`) | SCSS functions and utility mixins | Evolves, versioned | Projects pick what they need |
| **Project profile** | Token values, material assignments, active extensions | Per-engagement | Unique to each project |

**The spec** defines how CSS is structured: token layers, material harness, cascade strategy, SCSS boundaries, WordPress conventions. It shapes every selector in a project.

**The library** is a toolbox of SCSS functions and mixins that produce CSS output. A project may use colour generation, type scale functions, shadow generators, or none of them. Using a library function does not change how the system is organised. The library respects the spec's rules (functions produce CSS custom properties, not Sass variables consumed by selectors) but grows independently.

**The project profile** is a per-engagement document that records token values, material assignments, active extensions and library selections. See `PROJECT-PROFILE.md` for the template.

The spec references the library but does not depend on it. The library respects the spec but can evolve independently. The project profile depends on both.

## 1. Purpose and Principles

### 1.1 Purpose

A CSS-native design architecture for building coherent, themeable interfaces without reliance on:

- Utility class frameworks
- Component-scoped styling
- Excessive markup annotation
- Page builders

### 1.2 Principles

**Semantic tokens define meaning.** Tokens describe what something is, not how it looks. `--surface-1`, `--text-2`, `--border-subtle`, not `--blue-500`, `--grey-light`.

**Materials define rendering.** A material is a bundle of visual properties applied to a surface: background, colour, border, shadow, containment.

**Structure selects materials.** Materials are derived from HTML structure, nesting depth and theme scope. Not from classes applied to elements.

**The cascade is the system.** CSS cascade and inheritance are intentionally leveraged. No attempt is made to isolate styles per component.

**Single-property concerns are tokens. Multi-property concerns are mixins.** If a rendering behaviour can be expressed as a single CSS custom property, it belongs in the material harness as a token. If it requires multiple coordinated properties (e.g. clip-path + border-radius reset + drop-shadow substitution), it belongs in an SCSS mixin.

## 2. Token Architecture

### 2.1 Layer Model

| Layer | Prefix | Role |
|---|---|---|
| Semantic | (none) | The design system API. What components consume. |
| Primitive | `--sys-*` | Raw scales and ramps. Not consumed directly by components. |
| Component | `--comp-*` | Adapter layer for specific component contexts. Thin, not the default. |
| Capture | `--cap-*` | Theme boundary reversion (see Extension E3). |

The layer model is a naming convention. No CSS output is generated by the convention itself. Every project uses this prefix structure so that reading any Digitalis stylesheet tells you which layer you're operating in.

**How components adapt to surfaces:** Most components should read semantic tokens directly (`--text-1`, `--border-subtle`, `--accent`). When a `[data-theme]` scope redefines those tokens, the component adapts automatically via the cascade. No descendant selectors (e.g. `.dark .tag`) are needed.

When a component has its own foreground/background relationship that doesn't map directly to the semantic text/surface tokens (e.g. a tag with a tinted background and accent-coloured text), it defines component-layer tokens (`--comp-tag-bg`, `--comp-tag-fg`) whose values are set at `:root` and overridden inside theme scopes:

```css
:root {
    --comp-tag-bg: var(--accent-tint);
    --comp-tag-fg: var(--accent);
}

[data-theme="dark"] {
    --comp-tag-bg: var(--accent);
    --comp-tag-fg: #fff;
}

.tag {
    background: var(--comp-tag-bg);
    color: var(--comp-tag-fg);
}
```

The component itself has one rule. The theme scope handles the variation. This pattern replaces descendant selectors (`.dark .tag`, `.pair-card-dark .tag`) with cascade-driven token reassignment.

### 2.2 Single Source of Truth

Token values live in a CSS file as `:root` custom properties. There is no JSON mirror. The CSS file is the canonical source.

**PHP API:** A parser class exposes resolved token values to server-side code (templates, email output, PDF generation):

- `Tokens::get($name)` — returns the most-resolved value. Resolves `var()` chains iteratively (max 16 hops, throws on cycle). Literals returned as-is. Opaque expressions (`color-mix`, `calc`, multi-arg compositions) returned verbatim — caller decides what to do with them.
- `Tokens::raw($name)` — returns the literal text from `tokens.css` without resolution. Useful for round-tripping and debugging.
- Output cached against `tokens.css` mtime + content hash; invalidates automatically when the file changes.

The parser path defaults to `{plugin_dir}/assets/css/tokens.css`, configurable via filter. The parser is reliable because `tokens.css` is a controlled format authored by the developer: `--name: value;`, one declaration per line. No build step, no sync concern, one file.

**SCSS access:** SCSS treats tokens as opaque `var(--name)` references. The framework does not inject token values into the SCSS compiler. Library functions take values as Sass arguments from project SCSS rather than reaching into a global token namespace; compile-time token math is achieved at runtime via CSS-native functions (`color-mix(in oklab, ...)`, `calc()`, relative colour syntax). There is no parallel set of `$sass-variables` for design values.

### 2.3 Semantic Token Categories

Every project must define tokens in these categories. Values are per-project.

| Category | Required | Notes |
|---|---|---|
| Surfaces | Yes | Base plane + at least one additional context |
| Text | Yes | Foreground hierarchy (minimum 2 levels + inverse) |
| Borders | Yes | Minimum: subtle + strong |
| Interactive states | Yes | bg, bg-hover, bg-active, bg-disabled, fg, fg-disabled, focus-ring |
| Intent | Yes | Minimum: accent + contrast pair. Others as project requires. |
| Typography: stacks | Yes | Minimum: sans + mono |
| Typography: scale | Yes | Project defines steps and naming |
| Typography: weight | Yes | Project defines which weights to tokenise |
| Typography: line-height | Yes | Minimum: body, heading, dense |
| Spacing | Yes | Base unit (`--u`) with named multiplier stops (`--uN`). See Section 2.5. |
| Transitions | Yes | Minimum: duration-fast, duration-default, easing-default |
| Shadows / elevation | Optional | |
| Geometry | Optional | Only if the design direction uses structural shape (e.g. clip-path, specific radii) |
| Density contexts | Optional | Recommended when the project has both sparse and dense content patterns |

### 2.5 Spacing Convention

Spacing tokens use a base unit with named multiplier stops. No t-shirt sizing (`xs`, `sm`, `md`, `lg`). T-shirt names encode relative order but not meaning, cannot be extended without awkward names (`xxs`, `md-lg`), and produce unmaintainable systems.

**Base unit:**

```css
:root {
    --u: 0.5rem;    /* 8px at default root font-size */
}
```

**Named multiplier stops:**

```css
:root {
    --u2:  calc(var(--u) * 2);    /* 16px */
    --u3:  calc(var(--u) * 3);    /* 24px */
    --u4:  calc(var(--u) * 4);    /* 32px */
    --u7:  calc(var(--u) * 7);    /* 56px */
    --u12: calc(var(--u) * 12);   /* 96px */
}
```

**Fractional stops** use underscore notation. The number after the underscore is the denominator:

```css
:root {
    --u_4:  calc(var(--u) / 4);       /*  2px — border offsets */
    --u_2:  calc(var(--u) / 2);       /*  4px — tight gaps */
    --u3_2: calc(var(--u) * 3 / 2);   /* 12px — compact padding */
    --u5_2: calc(var(--u) * 5 / 2);   /* 20px — medium gaps */
}
```

The naming is self-documenting: `--u3_2` = 3/2u, `--u5_2` = 5/2u, `--u_4` = 1/4u. Integer stops and fractional stops use the same convention. No ambiguity, no naming collisions.

Projects define whichever stops they need. Gaps in the sequence are fine. New stops can be added at any time without renaming.

For one-off values, use `calc(var(--u) * N)` inline. No need to name every possible value.

The base unit is in `rem` so the spacing system respects user font-size preferences for accessibility. Changing `--u` scales the entire spacing system proportionally.

## 3. Material Harness

### 3.1 Core Harness

The material harness is a single rendering layer applied to structural elements. It handles single-property visual concerns only.

```css
:where(section, article, aside, header, footer, nav,
       fieldset, details, dialog, [data-surface]) {
    position: relative;
    isolation: isolate;

    background: var(--material-bg, transparent);
    color: var(--material-fg, inherit);
    border: var(--material-border, 0);
    box-shadow: var(--material-shadow, none);
}
```

**Material tokens:**

| Token | Property | Default |
|---|---|---|
| `--material-bg` | background | transparent |
| `--material-fg` | color | inherit |
| `--material-border` | border | 0 |
| `--material-shadow` | box-shadow | none |

All material tokens use fallback defaults so that unstyled structural elements render transparently. Material is applied by setting these tokens, not by adding classes.

**`isolation: isolate` and stacking contexts.** Every harnessed element creates its own stacking context. This is intentional. It makes z-index management predictable: a sticky nav with `z-index: 100` only needs to beat sibling sections, not deeply nested elements within them. Each section is a self-contained stacking context. Validated against the D-Pace moodboard's sticky nav + layered hero pattern.

**Layout is not material.** The harness handles rendering (how a surface looks). Layout properties (`position: sticky`, `z-index`, `display: grid`, `height`) are structural concerns that belong in project component SCSS, not in the harness. A `<nav>` gets its background, colour, border and shadow from the harness. Its sticky positioning, height and z-index are set in the project's nav component styles.

### 3.2 Containment

Content containment is a property of the material surface. Structural elements constrain their content using tokenised values:

```css
:where(main > section, main > article, main > aside) {
    padding-inline: max(
        var(--material-pad, 0px),
        calc((100% - var(--material-contain, 100%)) / 2 + var(--material-pad, 0px))
    );
}
```

**Containment tokens:**

| Token | Role | Default |
|---|---|---|
| `--material-contain` | Max content width | 100% (no constraint) |
| `--material-pad` | Minimum inline padding | 0px |

A surface with `--material-contain: 1200px` and `--material-pad: 56px` produces centred content with a 1200px max-width and 56px minimum side padding. No wrapper element required.

**Full-bleed children** that need to escape containment are handled as the exception (via mixin or targeted negative margin), not as the default. Containment is the norm; bleed is the escape.

### 3.3 Material Application

Materials are applied structurally, not via classes:

```css
/* Base plane */
body {
    background: var(--surface-0);
    color: var(--text-1);
}

/* Default content surface */
main > :where(section, article) {
    --material-bg: var(--surface-1);
    --material-border: 1px solid var(--border-subtle);
    --material-shadow: var(--shadow-1);
    --material-fg: var(--text-1);
}

/* Nested surface */
main > :where(section, article) :where(section, aside, fieldset) {
    --material-bg: var(--surface-2);
    --material-border: 1px solid var(--border-subtle);
    --material-shadow: none;
}
```

These examples are illustrative. Each project defines its own material assignments in its project profile.

## 4. Cascade and Specificity Strategy

**`:where()` for harness selectors.** The harness uses zero-specificity selectors so that project-level and component-level styles override without escalation.

**`[data-theme]` for theme scoping.** Theme overrides are scoped via data attributes, not classes. `[data-theme]` may be set statically in PHP templates or dynamically via JavaScript (e.g. a navigation bar that switches from dark to light on scroll). The mechanism is the same in both cases: the attribute changes, the cascade delivers new token values to all descendants. Components inside a theme scope never need to know how or when the scope was set.

**Doubled-class selectors for external library boundaries.** `.wrapper.wrapper {}` provides a controlled specificity boost without `!important`. See Section 8.

**No `!important`** except on token rebinding inside theme scopes where external library CSS forces escalation.

**Inheritance is intentional.** `color`, `font-family`, `line-height` and other inherited properties flow from material surfaces to their children. This is the mechanism, not a side effect.

## 5. SCSS Usage Rules

SCSS is used for composition. CSS custom properties are used for values. The boundary between them:

- **Single-property rendering concern** = CSS custom property in the material harness
- **Multi-property rendering concern** = SCSS mixin

### 5.1 Allowed

- Mixins for multi-property rendering compositions (shape, effects, overlay)
- `@use` / `@forward` for file organisation
- Nesting for structural readability
- Small utility mixins (visually-hidden, clearfix)
- Breakpoint and container query access mixins (see Section 6)
- Library functions that produce CSS custom properties (see Section 9)

### 5.2 Not Allowed

- Sass variables (`$var`) for design values. Token values reach SCSS via the PHP-to-SASSY pipeline (Section 2.2), not via `$variable` declarations in SCSS files.
- Variant generation via `@each` / `@for` producing class permutations
- Component-specific mixins tied to markup structure
- Token logic or conditionals in SCSS
- Utility classes generated from mixins

### 5.3 Multi-Property Mixin Pattern

When a rendering behaviour requires multiple coordinated CSS properties, it is encapsulated in a mixin. The mixin is the single place where the coordination logic lives.

Examples of multi-property concerns:

- Shape: clip-path + border-radius reset + shadow method substitution
- Frosted surface: backdrop-filter + translucent background + border treatment
- Texture overlay: pseudo-element setup + background-image + blend-mode + opacity
- Cover pseudo-elements: positioning + dimensions + pointer-events + z-index

```scss
// Example: shape mixin (project-specific values)
@mixin shape-chamfer {
    clip-path: var(--chamfer);
    border-radius: 0;
    // box-shadow is clipped — use filter: drop-shadow() instead
}
```

Each project defines its own composition mixins. The convention (multi-property = mixin) is shared. The contents are not.

## 6. Breakpoints and Container Queries

### 6.1 Breakpoints

Breakpoint values cannot live in CSS custom properties (media queries do not read them). Breakpoints are defined as an SCSS map with a shared access mixin.

**Convention (core):** mobile-first, min-width, semantic naming.

Breakpoint names describe layout context, not pixel values or t-shirt sizes. The name must remain accurate if the value changes.

```scss
// Default map — every project starts with this, adjusts as needed
$breakpoints: (
    mobile-port:  400px,     // small-screen tuck-in (360–400px range)
    mobile-land:  640px,     // landscape / large mobile
    tablet:       1024px,    // two-column layouts become viable
    desktop:      1440px,    // wide desktop
);

// Core: shared mixin interface
@mixin at($name) {
    @media (min-width: map-get($breakpoints, $name)) {
        @content;
    }
}
```

Projects add or remove breakpoints as needed (e.g. `tablet-land: 1200px` between tablet and desktop). The naming scheme is extensible because names describe context, not position in a sequence.

**Do not use:** `sm`, `md`, `lg` or numeric names like `bp-400`. T-shirt sizes cannot be extended without awkward names. Numeric names are labelled literals that add nothing over hardcoded values.

For range queries or max-width conditions, use CSS-native media query syntax directly. The `@mixin at()` covers the common case (min-width breakpoint). It does not attempt to replace the full media query language.

### 6.2 Container Queries

CSS containment (`container-type`) is applied deliberately per-component, not globally. It has performance implications and should not be set on every structural element.

Container query breakpoints follow the same convention as viewport breakpoints:

```scss
// Per-project: define the map
$container-breakpoints: (
    compact: 400px,
    medium: 600px,
    wide: 900px,
);

// Core: shared mixin interface
@mixin container-at($name) {
    @container (min-width: map-get($container-breakpoints, $name)) {
        @content;
    }
}
```

### 6.3 Summary

| Concern | Where it lives | Form |
|---|---|---|
| Breakpoint mixin interface | Core | SCSS mixin (`@mixin at`) |
| Breakpoint default map | Core | SCSS map (mobile-port, mobile-land, tablet, desktop) |
| Breakpoint overrides / additions | Per-project | SCSS map merge or replacement |
| Container query mixin interface | Core | SCSS mixin (`@mixin container-at`) |
| Container query values | Per-project | SCSS map |
| `container-type` declarations | Per-project | Applied to specific components in SCSS |

## 7. WordPress Markup Convention

### 7.1 Theme Templates

Theme templates are authored with semantic HTML. The material harness catches structural elements automatically.

```html
<!-- The harness targets section, article, aside, etc. -->
<section>
    <h2>...</h2>
    <p>...</p>
</section>
```

No page builders. Templates are custom PHP producing semantic markup.

### 7.2 CMS and Plugin Output

WordPress core, block editor output and plugins produce non-semantic wrappers (`div.wp-block-*`, `div.entry-content`, plugin-specific markup). When these need material treatment, they receive a `data-surface` attribute in the PHP template:

```html
<div class="wp-block-group" data-surface>
    ...
</div>
```

`[data-surface]` is included in the harness selector list. This is the escape hatch for non-semantic markup.

### 7.3 Content Editors

Content editors never apply styling classes or attributes. All visual behaviour derives from structure and theme scope. If an editor action needs to influence rendering, it does so via a structured field (e.g. an ACF select that maps to a `data-theme` value in the template), never via a class name.

## 8. External Library Integration

External libraries (Gravity Forms, WordPress block editor, plugins) are treated as styling islands.

### 8.1 Boundary

Use a doubled-class specificity boost at the boundary:

```css
.gform_wrapper.gform_wrapper {
    /* adapter rules */
}
```

### 8.2 Rules

- Do not disable functional CSS from the library unless fully replaced
- Override the visual layer only
- Use semantic tokens exclusively inside the boundary
- Avoid `!important` except on token rebinding where the library forces it

## 9. Entry Points

This section defines how tokens, mixins and components compose into final stylesheets per WordPress context.

### 9.1 Filesystem Layout

Two roots, separated by ownership:

| Root | Owner | Contains |
|---|---|---|
| `lattice-css/scss/` | Framework (own repo) | Architecture-level partials: `_harness.scss`, `_mixins.scss`, `lib/` |
| `scss/` | Project | Context entry points, components, integrations, project mixins |
| `assets/css/tokens.css` | Project | Single source of truth for token values |

The framework's `scss/` directory is added as a SASSY import path (via the `sassy-import-paths` filter), so projects write `@use 'harness'`, `@use 'lib/breakpoint'`, etc. without referencing the framework's mount location. Imports stay stable whether the framework is embedded, a sibling plugin, a submodule, or a vendored copy — only the integration that registers the import path changes.

### 9.2 Context Entry Points

Each WordPress context that needs CSS gets a top-level entry file in `scss/`:

| Entry | Loaded by | Purpose |
|---|---|---|
| `frontend.scss` | Theme `wp_enqueue_style` | Frontend pages |
| `editor.scss` | Block editor (`add_editor_style` or block `editor.css`) | Block editor canvas |
| `admin.scss` | Admin enqueue | Plugin admin pages |
| `print.scss` | Print stylesheet | Print contexts |

Naming describes the WordPress context, not the file role. Projects may add or remove entry points as needed.

### 9.3 Token Loading Model

Tokens flow through three channels from a single `tokens.css`:

| Channel | Mechanism | Consumer |
|---|---|---|
| Browser | Enqueued as standalone `<link>` stylesheet | All page contexts |
| PHP runtime | Parser API (`Tokens::get`, `Tokens::raw`) | Templates, email, PDF |
| SCSS | Opaque `var(--name)` references only | Library functions and components emit CSS using `var()` |

Compiled SCSS context entries do not inline token declarations. They rely on `tokens.css` being loaded earlier in the cascade. This guarantees zero duplication: every token exists in exactly one place.

### 9.4 Editor Scoping

The block editor wraps content in `.editor-styles-wrapper`. Every selector rule that should apply to editor content must be re-emitted under that wrapper. At-rules (`@font-face`, `@keyframes`) and root-level declarations (`:root`) cannot nest inside selector blocks — they stay top-level.

The mechanism is mixin-shaped framework parts:

```scss
// editor.scss
@use 'harness' as h;
@use 'components';
@use 'fonts';

@include fonts.declarations;          // @font-face top-level

.editor-styles-wrapper {
    @include h.harness;
    @include components.all;
}
```

Frontend uses the same partials but invokes them at top level:

```scss
// frontend.scss
@use 'harness' as h;
@use 'components';

@include h.harness;
@include components.all;
```

**Specificity note:** harness selectors use `:where()` for zero-specificity at the frontend top level. Inside `.editor-styles-wrapper`, the wrapper class adds `(0,1,0)` to harness rules. Project component CSS that overrides harness must clear `(0,1,0)` in editor contexts; in practice this is automatic because component selectors use a class.

**Fonts and other at-rules.** `@font-face` and `@keyframes` cannot nest inside selector blocks. The convention is to declare them inside a `@mixin` (e.g. `scss/_fonts.scss` exposing `@mixin declarations`) and have each entry point `@include` the mixin at top level — never inside `.editor-styles-wrapper` or another wrapper. Same shape as the selectors-only-via-mixins rule (§9.5), applied to at-rules. Self-host WOFF2 (variable fonts where available) with `font-display: swap`; preload primary faces via `wp_head`.

### 9.5 Selectors-Only-Via-Mixins Convention

**Every framework partial and every project component partial that emits selectors must do so inside a `@mixin`, not at file top level.**

The rule exists so contexts can re-emit the same selector logic under different scope wrappers (frontend at top level, editor inside `.editor-styles-wrapper`). A partial that declares selectors at top level cannot be wrapped without duplication.

**Corollary: component partials do not declare `:root` rules.** Component-layer token defaults (`--comp-tag-bg`, etc.) live in `tokens.css`, the project's source of truth. Component partials only declare selector rules that consume those tokens. The reason is mechanical: `:root` cannot be nested inside a selector — `.editor-styles-wrapper :root { ... }` matches nothing.

Theme-scope rules (`[data-theme="dark"] .tag { ... }`) are fine inside component mixins; they wrap correctly to `.editor-styles-wrapper [data-theme="dark"] .tag { ... }` and only fire when the editor body carries the attribute.

### 9.6 Component Organisation

Project components live in `scss/components/`, one partial per component, aggregated via an `_index.scss` that exposes a single `@mixin all`:

```scss
// scss/components/_tag.scss
@mixin component {
    .tag { /* selectors only */ }
    [data-theme="dark"] .tag { /* OK: scoped via wrapper */ }
}

// scss/components/_index.scss
@use 'tag';
@use 'form';

@mixin all {
    @include tag.component;
    @include form.component;
}
```

The framework prescribes the convention (one mixin per partial, `_index.scss` aggregates). The project owns the file list. Same pattern for `scss/integrations/`.

Context entry points include only the integration partials they need: `frontend.scss` includes Gravity Forms, `editor.scss` does not.

### 9.7 Build

SASSY compiles SCSS on-demand in both development and production, using its existing transient cache (filemtime checks + signature hashing). Compiled CSS files are not committed to source control — SCSS is the source of truth, compiled output is an artifact. Re-running compilation regenerates them deterministically.

The PHP token parser caches its output keyed on `tokens.css` mtime + content hash. The cache flushes naturally when the tokens file changes.

For deploy-time cold-start mitigation, run `wp sassy compile` in deployment hooks to prime the cache before serving traffic.

## 10. Library

The library (`lib/`) is a collection of SCSS functions and utility mixins shared across projects. It is versioned independently of the spec. Projects `@use` the partials they need.

### 10.1 Library Scope

The library contains reusable SCSS functions and mixins that produce CSS output. It does not contain architecture (that's the spec) or project-specific values (that's the project profile).

**Available partials:**

| Partial | Surface | Origin |
|---|---|---|
| `_var.scss` | `v($name, ...)` — CSS variable shorthand with chained-fallback support | Ported from legacy `lib/utils/var.scss`; `alt()` removed (legacy theming pattern superseded by `[data-theme]`-driven token reassignment) |
| `_breakpoint.scss` | `at($name)`, `container-at($name)` — viewport and container query mixins; default `$breakpoints` map | New (defined in §6) |
| `_color.scss` | `mix($a, $b, $stop)`, `tints($base, $n)`, `shades($base, $n)` — runtime mixing via `color-mix(in oklab, ...)` | Refactored from legacy `generate-mix.scss` / `generate-shades.scss`; reoriented to values-in/values-out, no property emission, no name baking |
| `_type.scss` | `ratio($name)`, `step($base, $ratio, $level)`, `text-clip` mixin | Refactored from legacy `generate-headings.scss` / `text-clip.scss`; project composes `clamp()` from `step()` outputs |
| `_shadow.scss` | `box`/`drop`/`text` (functions and mixins) — multi-layer perceptually-eased shadows for box-shadow / filter / text-shadow | Refactored from legacy `soft-shadow.scss` / `soft-drop-shadow.scss` / `soft-text-shadow.scss`; deduplicated easing helpers, single recipe |
| `_geometry.scss` | `chamfer($d)` — clip-path with octagonal cut corners | Ported from legacy `clip-path.scss`; renamed to align with spec naming |

### 10.2 Library Rules

- Functions are values-in / values-out: they take Sass-typed arguments and return Sass values (lists, maps, expressions). They do not write CSS custom properties as a side effect, do not reach into a global token namespace, and do not generate selector variants.
- Mixins set CSS properties only when that's the function's purpose (e.g. `text-clip`, `chamfer`); they do not declare selectors.
- No library partial may depend on project-specific token names or values. Defaults are literal Sass values; if a project wants a token wired in, that's a project mixin one layer up.
- Library partials must be independently `@use`able. No implicit dependency ordering.

### 10.3 Library vs. Project Mixins

The library contains **project-agnostic** functions: generate a colour scale, produce a shadow, calculate a type ramp. These work regardless of the project's design direction.

**Project-specific** mixins (e.g. `shape-chamfer`, `material-card`) live in the project's own SCSS, not in the library. They reference project tokens and are not portable.

## 11. Extension Modules

These are opt-in per project. A project's profile declares which extensions it uses.

### E1. Overlay / Effects System

SCSS mixins for multi-property rendering effects:

- Frosted surface (backdrop-filter + translucent bg + border)
- Texture overlay (pseudo-element + background-image + blend-mode)
- Shape compositions (clip-path, radius, shadow method coordination)
- Cover pseudo-elements (absolute positioning + inset + pointer-events)

Each mixin is self-contained. A project includes only the ones its design direction requires.

When a project uses the overlay extension on structural elements, the `::before` pseudo-element is reserved for the overlay layer:

```css
:where(section, article, aside, header, footer, nav,
       fieldset, details, dialog, [data-surface])::before {
    content: "";
    position: absolute;
    inset: var(--material-overlay-inset, 0);
    border-radius: var(--material-overlay-radius, inherit);
    background: var(--material-overlay-bg, transparent);
    opacity: var(--material-overlay-opacity, 0);
    mix-blend-mode: var(--material-overlay-blend, normal);
    pointer-events: none;
    z-index: 0;
}
```

With content raised above:

```css
:where(section, article, aside, header, footer, nav,
       fieldset, details, dialog, [data-surface]) > * {
    position: relative;
    z-index: 1;
}
```

And backdrop-filter support:

```css
@supports (backdrop-filter: blur(1px)) {
    :where(section, article, aside, header, footer, nav,
           fieldset, details, dialog, [data-surface])::before {
        backdrop-filter: var(--material-backdrop-filter, none);
    }
}
```

Projects that do not use overlay effects do not include this CSS. The `::before` pseudo-element remains available for other uses.

### E2. Density Context System

A mechanism for switching spacing and type tokens in dense content areas:

```css
[data-density="compact"] {
    --space-block: var(--sys-space-xs);
    --font-meta: var(--sys-font-sm);
    /* project defines which tokens shift */
}
```

Recommended for projects with high information-density pages alongside scannable entry pages. Applied via `data-density` attribute in templates.

### E3. Capture / Hole Theme Boundary

For deeply nested theme inversions where a child context needs to revert to the parent theme:

```css
/* Capture: save current values at the theme boundary */
[data-theme] {
    --cap-surface-0: var(--surface-0);
    --cap-text-1: var(--text-1);
    /* capture all tokens that may need reversion */
}

/* Hole: revert to captured values */
.hole {
    --surface-0: var(--cap-surface-0);
    --text-1: var(--cap-text-1);
}
```

Most projects will not need this. Available when a design requires a "window" back to the parent theme context inside an inverted section.

### E4. Material Composition Mixins

Per-project SCSS mixins that bundle a material assignment for reuse:

```scss
@mixin material-card {
    --material-bg: var(--surface-2);
    --material-border: 1px solid var(--border-subtle);
    --material-shadow: var(--shadow-1);
}
```

The convention is shared (this is how you bundle material assignments). The contents are project-specific.

## 12. Validation: Stress Test Results

The spec was stress-tested against the D-Pace Signal Clear Stage 2 moodboard. Three components were run through the material harness, cascade and theme scoping model.

### 12.1 Tag Component

**Challenge:** The tag has its own background/foreground pair that differs from the surface it sits on. It also appears on three surface contexts (light, dark, muted-dark) in the moodboard.

**Result:** The `--comp-*` layer (Section 2.1) handles this cleanly. The tag defines `--comp-tag-bg` and `--comp-tag-fg`, which are reassigned inside `[data-theme]` scopes. One selector for the tag, one override per theme. No descendant selectors needed.

**Open item:** The moodboard has a third tag treatment (muted-dark, in the pair-card layout) that is neither the standard light nor dark variant. This requires a design decision: is it a distinct theme scope (e.g. `[data-theme="dark-muted"]`) or a moodboard artifact that won't survive into production?

### 12.2 Spec Table

**Challenge:** High-density structured data with technical formatting (superscripts, subscripts, dual-unit notation). Appears on product detail pages alongside lower-density content.

**Result:** Best-case scenario for the spec. The table reads semantic tokens (`--text-1` for values, `--text-2` for labels, `--border-subtle` for hairlines, `--accent-tint` for hover). If the surface redefines those tokens via `[data-theme]`, the table adapts with zero additional CSS.

**Density:** The density extension (E2) applies here. A `[data-density="compact"]` scope around the table reassigns spacing and font-size tokens. The table component itself doesn't change.

**Typography:** Superscript/subscript rendering (`1×10⁻⁸ mbar`, `H₂⁺`) is a project-profile concern, not an architectural gap. The `--leading-dense` token value must be chosen to accommodate `<sup>` and `<sub>` without clipping. `font-variant-numeric: tabular-nums` in spec table contexts keeps column alignment stable.

### 12.3 Navigation (Surface Transition)

**Challenge:** Sticky nav that switches between dark (default) and light (on scroll) via JavaScript.

**Result:** The nav is a `<nav>` element caught by the harness. It gets `--material-bg`, `--material-fg`, `--material-border` from its default dark material assignment. On scroll, JS sets `data-theme="light"`, and the cascade delivers new token values to all descendants. Links use `color: inherit` with opacity for inactive/active states. The moodboard's 4 descendant selectors for light/dark nav links reduce to inherited colour + opacity.

**Layout/material separation validated:** The nav's `position: sticky`, `z-index: 100` and `height: 60px` are layout concerns handled in project component SCSS. The harness provides only the rendering surface. `isolation: isolate` on sections makes the nav's z-index predictable.

### 12.4 Summary

| Concern | Verdict |
|---|---|
| Material harness on surfaces | Holds. Ground, paper, dark map to theme scopes. |
| Cascade for component theming | Holds. Components read semantic or `--comp-*` tokens. No descendant selectors. |
| Containment via `max()` padding | Holds. Matches the moodboard's 1200px/56px pattern. Nav uses the same values. |
| `isolation: isolate` on all structural elements | Beneficial. Predictable z-index for sticky nav. |
| Density extension (E2) | Needed for D-Pace. Spec tables and product detail pages are the use case. |
| `[data-theme]` dynamic switching | Works. JS sets the attribute, cascade delivers. Components don't need to know. |
| Layout vs. material boundary | Clear. Harness handles rendering. Layout properties are project component SCSS. |

## 13. What This Spec Does Not Cover

These are per-project concerns, defined in the project profile:

- Token values
- Component CSS
- Grid and layout systems
- Responsive breakpoint values
- Animation and motion beyond transition tokens
- Specific typography choices
- Specific colour palettes

## Open Questions

1. **Named container queries.** Should the core mixin support named containers (`@container sidebar (min-width: ...)`), or is unnamed sufficient?
2. **The harness selector list.** Is the current list (`section, article, aside, header, footer, nav, fieldset, details, dialog, [data-surface]`) complete, or should `main` and `form` be included?
3. **Complex component patterns.** Tabs, accordions, modals and carousels need validation against the material/cascade model. Deferred until the first project profile stress-tests them.
4. **Performance.** `isolation: isolate` on every structural element creates stacking contexts. Confirmed beneficial for z-index management (Section 12.3). Still worth validating on content-heavy pages with many nested sections.
5. **Muted-dark component variants.** The D-Pace moodboard uses a third tag treatment (muted-dark in pair-card layout) that is neither the standard light nor dark variant. Is this a distinct theme scope, a component-level `--comp-*` override, or a moodboard artifact? Design decision needed before the D-Pace project profile can fully resolve the `--comp-tag-*` tokens.
6. **Opacity scale on dark surfaces.** The moodboard uses 7+ distinct alpha values for text on dark backgrounds (0.28, 0.35, 0.4, 0.55, 0.6, 0.75, 0.85, 0.95). These should collapse into a defined `--text-1` / `--text-2` / `--text-3` hierarchy within the dark theme scope. The project profile needs to rationalise this into a small set of semantic text tokens rather than carrying ad-hoc opacity values.
